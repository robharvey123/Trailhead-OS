## Brief 1: outreach schema migration

**Goal.** Add the tables that let any future campaign be defined as an audience, a set of templates and an ordered list of steps, plus per-recipient state and a global suppression list.

**Files to touch.**

- `supabase/migrations/20260725100000_outreach_engine.sql` (new)
- `lib/types.ts` (append types)

**Changes.**

1. New migration, following repo convention: `create table if not exists`, `drop policy if exists` before `create policy`, and `update_workspace_updated_at()` for every `updated_at` trigger. Do not invent `update_updated_at()`; it does not exist.

2. Extend `contacts` for outreach and call compliance:

```sql
alter table contacts
  add column if not exists email_greeting text,
  add column if not exists do_not_email boolean not null default false,
  add column if not exists do_not_call boolean not null default false,
  add column if not exists ctps_registered boolean,
  add column if not exists ctps_checked_at timestamptz;
```

`email_greeting` holds the merge-tag salutation ("Ian", or "there" when no name is published), so no code has to guess a first name by splitting `contacts.name`.

3. New tables. Single-tenant, so no workspace or org column anywhere.

- `outreach_audiences` (`id`, `name` unique, `description`, `created_at`)
- `outreach_audience_members` (`audience_id`, `contact_id`, `added_at`, primary key on the pair). Static membership by design: a snapshot you can reason about beats a live filter that silently changes who is mid-sequence.
- `outreach_templates` (`id`, `name` unique, `subject`, `body_html`, `body_text`, `created_at`, `updated_at`)
- `outreach_campaigns` (`id`, `name`, `project_id` references `projects(id) on delete set null`, `audience_id` references `outreach_audiences(id)`, `status` check in `draft, scheduled, running, paused, completed, cancelled` default `draft`, `from_name`, `from_email`, `reply_to`, `daily_send_cap` int default 20, `send_window_start` time default `07:30`, `send_window_end` time default `16:00`, `send_days` int[] default `{2,3,4}` for Tue to Thu using ISO day numbers, `timezone` text default `Europe/London`, `started_at`, `completed_at`, `created_at`, `updated_at`)
- `outreach_campaign_steps` (`id`, `campaign_id` cascade, `step_number` int, `template_id` references `outreach_templates(id)`, `delay_days` int default 0, unique on `(campaign_id, step_number)`)
- `outreach_recipients` (`id`, `campaign_id` cascade, `contact_id` references `contacts(id) on delete cascade`, `status` check in `pending, active, completed, stopped` default `pending`, `current_step` int default 0, `next_send_at` timestamptz, `stopped_reason` check in `replied, unsubscribed, bounced, complained, manual, converted` nullable, `stopped_at`, `unsubscribe_token` uuid not null default `gen_random_uuid()` unique, `created_at`, unique on `(campaign_id, contact_id)`)
- `outreach_sends` (`id`, `campaign_id`, `recipient_id` cascade, `step_id`, `resend_email_id` text, `subject`, `status` check in `queued, sent, delivered, opened, clicked, bounced, complained, failed` default `queued`, `sent_at`, `delivered_at`, `first_opened_at`, `first_clicked_at`, `error`, `created_at`)
- `outreach_events` (`id`, `send_id` references `outreach_sends(id) on delete cascade`, `resend_email_id` text, `type` text, `payload` jsonb, `occurred_at` timestamptz, `created_at`). Raw webhook landing table, never updated.
- `email_suppressions` (`id`, `email` text not null, `reason` check in `unsubscribed, bounced, complained, manual`, `source` text, `notes` text, `created_at`) with `create unique index on email_suppressions (lower(email))`.

4. Indexes that matter: `outreach_recipients (campaign_id, status, next_send_at)` for the scheduler's due query, `outreach_sends (resend_email_id)` for webhook lookup, `outreach_events (resend_email_id)`, `outreach_audience_members (contact_id)`.

5. RLS. Match `20260604090100_rls_lockdown.sql` exactly. All `outreach_*` tables and `email_suppressions` get the employee pattern, since the follow-up caller is an `employee` and needs to read recipients and write call outcomes:

```sql
alter table outreach_campaigns enable row level security;
drop policy if exists outreach_campaigns_employee_rw on outreach_campaigns;
create policy outreach_campaigns_employee_rw on outreach_campaigns for all to authenticated
  using (is_employee()) with check (is_employee());
```

Repeat per table. `is_employee()` already exists and covers owner, admin and employee. Contractors get nothing, which is the intended fail-closed behaviour.

6. Append the matching TypeScript types and status const arrays to `lib/types.ts`, following the `ENGAGEMENT_TASK_STATUSES` pattern (exported array plus a `Record` of labels).

**Verify.** `npx supabase db push` applies cleanly, then rerun it: the migration must be idempotent. Then confirm as a non-admin employee user that `select * from outreach_campaigns` succeeds and as an unauthenticated client that it returns nothing.

**Watch out for.** `contacts` is in the `employee_tables` array of the lockdown migration, so its policy is already `contacts_employee_rw`. Adding columns does not change that; do not add a second policy. `outreach_events` will grow fast, so do not add a foreign key from it to `outreach_recipients` as well; `send_id` is enough.

## Brief 2: Resend send layer, webhook, unsubscribe

**Goal.** Send one campaign email through Resend from the campaign's own sending identity, record the send, and ingest Resend's delivery events back onto that record.

**Files to touch.**

- `lib/outreach/send.ts` (new)
- `lib/outreach/render.ts` (new)
- `app/api/webhooks/resend/route.ts` (new)
- `app/api/outreach/unsubscribe/[token]/route.ts` (new)
- `app/(public)/unsubscribed/page.tsx` (new)
- `middleware.ts` (edit)
- `.env.example` (edit)

**Changes.**

1. `lib/outreach/render.ts`: a single `renderTemplate(body: string, vars: Record<string, string>)` that replaces `{{key}}` tokens. Supported vars: `email_greeting`, `company`, `name`, `city`, `channel`, `sub_trade`, `size_signal`. Any unresolved token must throw rather than send `{{company}}` to a prospect. HTML-escape every substituted value.

2. `lib/outreach/send.ts`: `sendCampaignEmail({ recipientId })`. It loads the recipient, contact, campaign and current step's template; checks `email_suppressions` by `lower(email)` and `contacts.do_not_email`; renders subject and body; then calls `resend.emails.send` with:
   - `from: \`${campaign.from_name} <${campaign.from_email}>\``
   - `replyTo: campaign.reply_to`
   - `headers`: `List-Unsubscribe: <https://app.trailheadholdings.uk/api/outreach/unsubscribe/${recipient.unsubscribe_token}>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`
   - `tags: [{ name: 'campaign', value: campaign.id }, { name: 'recipient', value: recipient.id }]`
   
   Insert an `outreach_sends` row with the returned `id` as `resend_email_id`. Reuse the existing client from `lib/email/resend.ts`; it is already exported as `resend` and is `null` when `RESEND_API_KEY` is unset, so guard for null.
   
   Append a visible unsubscribe line and the registered trading address to the footer of `body_html`. Both are legally required and both help deliverability.

3. `app/api/webhooks/resend/route.ts`: `POST` only. Read the raw body with `await request.text()` before any JSON parse. Verify with the Resend SDK's `resend.webhooks.verify()` if the installed version (`resend@^6.8.0`) exposes it; check `node_modules/resend` first and fall back to the `svix` package with `svix-id`, `svix-timestamp` and `svix-signature` if it does not. Handle these event types verbatim: `email.sent`, `email.delivered`, `email.opened`, `email.clicked`, `email.bounced`, `email.complained`, `email.failed`, `email.delivery_delayed`. For each: insert into `outreach_events`, then update the matching `outreach_sends` row by `resend_email_id`. On `email.bounced` or `email.complained`, additionally insert into `email_suppressions` and set the recipient to `status = 'stopped'` with the corresponding `stopped_reason`. Use `supabaseService` from `lib/supabase/service.ts`; there is no user session on a webhook.

4. `app/api/outreach/unsubscribe/[token]/route.ts`: handle both `GET` (click) and `POST` (one-click). Look up the recipient by `unsubscribe_token`, insert the contact's email into `email_suppressions` with `reason = 'unsubscribed'`, set `contacts.do_not_email = true`, set the recipient to `stopped` with `stopped_reason = 'unsubscribed'`, then redirect `GET` to `/unsubscribed`. Always return 200 even for an unknown token, so the endpoint cannot be used to enumerate recipients.

5. `middleware.ts`, two edits, both essential:
   - Add `/api/webhooks/resend` and `/api/outreach/unsubscribe` to `publicApiPrefixes`.
   - Add `/unsubscribed` to `publicRoutes`.
   
   Without these, the middleware redirects the webhook to `/login` with a 307 and Resend records every delivery event as failed. This is the exact failure the existing comment in that file describes for `/api/cron/*`.

6. `.env.example`: add `RESEND_WEBHOOK_SECRET`, `OUTREACH_FROM_EMAIL`, `OUTREACH_FROM_NAME`, `OUTREACH_REPLY_TO`, and `CRON_SECRET` (which is missing today despite being required by every cron route).

**Verify.** Send one test email to your own address through `sendCampaignEmail`, confirm an `outreach_sends` row appears, then open it and confirm an `email.opened` event lands in `outreach_events` and sets `first_opened_at`. Click the unsubscribe link and confirm the suppression row, the `do_not_email` flag and the stopped recipient. Then attempt a second send to that address and confirm it is refused.

**Watch out for.** `config.matcher` in `middleware.ts` currently excludes only `api/webhooks/stripe`. Adding to `publicApiPrefixes` is enough because the middleware returns early for public API prefixes, but confirm by curling the webhook path and checking you get a 400 from your handler rather than a 307. The `/unsubscribed` page must be reachable on the app subdomain: the non-app host is treated as the marketing site and any unrecognised path there is redirected to `/`, so the unsubscribe URL must be absolute and point at `app.trailheadholdings.uk`.

## Brief 3: the scheduler

**Goal.** A cron that walks each running campaign, works out who is due, respects the daily cap and send window, and advances or stops each recipient.

**Files to touch.**

- `app/api/cron/outreach-send/route.ts` (new)
- `lib/outreach/scheduler.ts` (new)
- `vercel.json` (edit, subject to Brief 0)

**Changes.**

1. Copy the auth and optimistic-claim shape from `app/api/cron/scheduled-send/route.ts`. Same bearer check against `CRON_SECRET`, same `maxDuration = 60`.

2. `lib/outreach/scheduler.ts` exports `runOutreachTick()`:
   - Load campaigns with `status = 'running'`.
   - For each, skip unless the current time in `Europe/London` falls inside `send_window_start` to `send_window_end` and the ISO weekday is in `send_days`.
   - Count sends already made today for that campaign from `outreach_sends` where `sent_at >= start of today London`. Remaining budget is `daily_send_cap` minus that count. Skip if zero.
   - Select recipients where `campaign_id` matches, `status in ('pending','active')` and `next_send_at <= now()`, limited to the remaining budget.
   - Before each send, run the stop checks in this order and stop the recipient if any hits: suppressed email, `contacts.do_not_email`, or an inbound reply. The reply check is a query against `email_logs` for `direction = 'inbound'` and `contact_id = <contact>` with `received_at >= recipient.created_at`. That table is already populated every 5 minutes by `gmail-sync`, so replies to the reply-to address stop the sequence with no extra plumbing.
   - Claim optimistically before sending, exactly as `scheduled-send` does: update `status` from its current value to `'active'` with `next_send_at = null` guarded by `.eq('status', previousStatus)`, and skip the row if the update returns no rows.
   - Call `sendCampaignEmail`, then set `current_step = current_step + 1`. If a next step exists, set `next_send_at = now() + delay_days` of that step and leave `status = 'active'`. If not, set `status = 'completed'`.
   - Throttle to at most 2 sends per second. Resend's default limit is 5 requests per second per team and other parts of the app share that budget.

3. Add to `vercel.json`: `{ "path": "/api/cron/outreach-send", "schedule": "*/15 * * * *" }`. That makes eight crons, which is fine on the current plan given seven already run at these frequencies.

**Verify.** Create a two-step test campaign with an audience of one (your own address), `daily_send_cap = 2` and `delay_days = 0` on step 2. Trigger the route manually with the bearer token. Confirm step 1 sends, the recipient advances to step 2, the second tick sends step 2 and the recipient lands on `completed`. Then reply to the step 1 email from another account, wait for `gmail-sync`, and confirm the recipient stops with `stopped_reason = 'replied'` instead of receiving step 2.

**Watch out for.** Do the send-window and day-of-week arithmetic in `Europe/London`, not UTC. In late July the offset is +1, so a naive UTC comparison sends an hour early and, worse, silently changes behaviour at the October clock change. Use `Intl.DateTimeFormat` with an explicit `timeZone`, not `new Date()` arithmetic. Also make the tick idempotent under overlap: a 15-minute schedule and a 60-second budget should never collide, but the optimistic claim is what actually guarantees no double-send, so do not skip it.
